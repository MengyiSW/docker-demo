Platform

Docker on Linux, Mac & Windows

Docker Engine (dockerd) is the server-side daemon that actually builds and runs containers. Where it runs depends on your OS.

🐧 Linux
Native

Docker Engine runs natively on the host OS. Containers use Linux kernel features (cgroups, namespaces) directly — no VM, no overhead.

dockerd on host No VM Full performance
🍎 macOS
Docker Desktop

Since macOS has no Linux kernel, Docker Desktop spins up a small Linux VM behind the scenes. Docker Engine runs inside it — you never notice it's there.

Linux VM Docker Desktop
🪟 Windows
Desktop / WSL2

Windows needs the same Linux layer. DInstall Docker Engine directly inside a WSL2 Linux distro. ⚠️ DO NOT USE DOCKER DESKTOP!

WSL2 Engine
Key insight: The Docker CLI is just a client — it talks to dockerd via a socket. Whether that daemon runs on bare metal or inside a VM is completely transparent to you.

Core Concept 01 / 04

Image

docker image

A read-only template that contains everything needed to run an application: code, runtime, libraries, environment variables, and config files. Images are built in layers — each instruction in a Dockerfile adds a layer.

postgres:16 nginx:alpine node:20-slim python:3.12
Think of it as: a recipe (or a class in OOP). It defines what the running thing will look like, but isn't running itself.
# List images on your machine $ docker images REPOSITORY TAG IMAGE ID SIZE postgres 16 a3f9… 428MB
Image Slide 08 / 20
Core Concept 02 / 04

Container

docker container

A running instance of an image. When you start a container, Docker creates an isolated process with its own filesystem (copied from the image), network interface, and process space.

Image vs Container is like Class vs Object in OOP. The image is the blueprint; the container is the live instance. You can run many containers from one image.
# List running containers $ docker ps CONTAINER ID IMAGE STATUS NAMES d7f3a1b2e9c4 postgres:16 Up 2 minutes mypostgres

Core Concept 03 / 04

Docker Engine

dockerd

The core runtime that builds and runs containers. It uses a client-server architecture with three components: the Docker Daemon (dockerd), the Docker CLI, and a REST API that connects them.

Components
  • ▸Docker Daemon (dockerd) — the server process that manages containers, images, and networks
  • ▸Docker CLI (docker) — the command-line tool you interact with
  • ▸REST API — the interface between CLI and daemon
# You type: $ docker run postgres
# CLI → REST API → dockerd # dockerd pulls image, creates # container, starts process

Registry

docker registry

A storage and distribution system for Docker images. Think of it as npm or PyPI, but for container images. The default public registry is Docker Hub.

Public registries
Docker Hub GitHub GHCR
Private registries
AWS ECR Azure ACR GCP Artifact Registry
# Download from registry $ docker pull postgres:16
# Upload to registry $ docker push myapp:v1.0

Demo — Step 2 / 3

Run a PostgreSQL Container

Terminal — run container
$ docker run \ -d # detached (background) --name mypostgres # give it a friendly name -e POSTGRES_USER=admin # set username -e POSTGRES_PASSWORD=secret # set password -e POSTGRES_DB=mydb # create default DB -p 5432:5432 # map host:container port postgres:16
-p 5432:5432 — left side is your local port, right side is the port inside the container. You connect to localhost:5432 as usual.

Demo — Step 3 / 3

Verify & Connect

Check it's running
$ docker ps # Stop and remove $ docker stop mypostgres $ docker rm mypostgres
Connect via psql
$ psql -h localhost -p 5432 -U admin -d mydb # -h host -p port -U user -d database   mydb=# \l # list databases mydb=# SELECT version(); mydb=# \q # quit psql
Or connect from your host with any client (DBeaver, TablePlus, psql) at localhost:5432 using user admin / password secret.

Useful Commands

System & Disk
# Disk usage breakdown $ docker system df   # Remove ALL unused objects (images, containers, networks) $ docker system prune -a   # Remove only dangling images $ docker image prune   # Remove unused volumes $ docker volume prune   # List networks / volumes $ docker network ls $ docker volume ls
Inspection & Ops
# Pull image from registry $ docker pull nginx:alpine   # Stream container logs $ docker logs -f <name>   # Live CPU / memory per container $ docker stats   # Full JSON details of container or image $ docker inspect <name>   # Tag & push to a registry $ docker tag myapp:latest user/myapp:v1 $ docker push user/myapp:v1

Wrap Up

Summary & Next Steps

What We Covered

The Problem — "works on my machine" eliminated by packaging app + deps together

Core concepts — Image (blueprint), Container (running instance), Docker Engine (daemon + CLI), Registry (image store)

PostgreSQL demo — pulled, ran, connected, and cleaned up a database in minutes

Key Takeaways

Isolation — each container gets its own filesystem, network, and process space; no interference with the host

Portability — same image runs identically on dev laptop, CI server, and production host

Ephemerality — containers are disposable; state lives in volumes, not in the container itself

Next Steps
